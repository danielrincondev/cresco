Parte 1 — Contexto del proyecto

1.1 Qué construimos

App Android de comunicación entre docentes y representantes legales de escuelas del Ecuador, para seguimiento de conducta. El estudiante nunca usa la app.

Dos interfaces: la del docente (herramienta de trabajo) y la del representante (informativa, simple).

1.2 El puntaje, en resumen

Cada estudiante parte de 60 puntos cada parcial. Piso 0, techo 100. Las acciones positivas suman (+1 o +2), las negativas restan (−1 a −3), con topes de +4 y −5 por día. Ese motor lo construye Persona B, pero tú necesitas conocerlo porque la matrícula que tú creas es la que lo sostiene.

3.2 Conceptos que necesitas entender antes de escribir código

¿Qué es un ORM? Una capa que te deja hablar con la base de datos usando TypeScript en vez de escribir SQL a mano. Drizzle es especial porque los tipos salen del esquema: si renombras una columna, el compilador te avisa en todos los lugares que la usaban.

¿Qué es una migración? Un archivo SQL que lleva la base de datos de un estado al siguiente. Nosotros no las escribimos: las genera drizzle-kit leyendo el esquema. Nunca las edites a mano.

¿Qué es RLS? Row Level Security. Reglas dentro de PostgreSQL que filtran qué filas puede ver cada usuario, aunque la aplicación se equivoque. Es nuestra segunda línea de defensa.

¿Qué es BetterAuth? Una librería que resuelve registro, inicio de sesión y sesiones. Crea sus propias tablas (user, session, account, organization, member). Nuestra tabla perfil_usuario las extiende con cédula y teléfono; nunca duplica lo que ya está en user.

4.1 — Corrección: fechas que pueden capturar el día equivocado.
matricula.fecha_ingreso y asignacion_docente.vigente_desde son columnas date con .defaultNow(). En Postgres, now() convertido a date se resuelve según el timezone de la sesión de la base de datos — típicamente UTC en un proveedor cloud. Ecuador es UTC-5, así que una matrícula creada entre las 19:00 y las 23:59 hora de Guayaquil queda fechada al día siguiente, en silencio. La regla "todo en UTC, la conversión ocurre en la pantalla" (§5, más abajo) es correcta para timestamptz, pero no cubre este caso de columnas date.

Ya está corregido (decisión E1, aplicada el 8 de agosto). Las dos columnas quedaron NOT NULL sin default, a propósito: obligan a que el servidor pase la fecha calculada con REGLAS.ZONA_HORARIA (America/Guayaquil). En el SQL se ve así: "fecha_ingreso" date NOT NULL.

Si te topas con un error tipo "null value in column fecha_ingreso violates not-null constraint", la respuesta correcta no es devolver el .defaultNow() — es pasar la fecha desde el servidor. Devolver el default reintroduce el bug en silencio.

Miércoles 12 — La capa de acceso

Esta es la parte más importante de tu trabajo en todo el proyecto.

Crea la carpeta db/acceso/ con funciones que siempre filtran por vínculo:

// db/acceso/estudiantes.ts
export async function estudiantesDelRepresentante(userId: string) {
  return db
    .select()
    .from(estudiante)
    .innerJoin(vinculoRepresentacion, eq(vinculoRepresentacion.estudianteId, estudiante.id))
    .innerJoin(representante, eq(representante.id, vinculoRepresentacion.representanteId))
    .where(and(
      eq(representante.userId, userId),
      eq(vinculoRepresentacion.estado, "ACTIVO"),
    ));
}

Regla que anuncias al equipo: está prohibido usar db.select() suelto sobre estudiante, matricula, accion_registrada o reporte_estudiante fuera de db/acceso/. Tú rechazas cualquier PR que lo haga.

Éxito: existe al menos una función de acceso por cada tabla sensible.

Jueves 13 y viernes 14 — RLS

Escribe las políticas para las cinco tablas críticas. Patrón:

ALTER TABLE estudiante ENABLE ROW LEVEL SECURITY;

CREATE POLICY p_representante_lee_estudiante ON estudiante
FOR SELECT USING (
  EXISTS (
    SELECT 1 FROM vinculo_representacion v
    JOIN representante r ON r.id = v.representante_id
    WHERE v.estudiante_id = estudiante.id
      AND v.estado = 'ACTIVO'
      AND r.user_id = current_setting('app.user_id', true)
  )
);

Cada petición debe abrir su transacción con:

SET LOCAL app.user_id = '<id del usuario>';
Consejo: si olvidas fijar la variable, la consulta devuelve cero filas en vez de todas. Eso es intencional: falla de forma visible y segura.

4.3 — Corrección: estudiantes sin documento pueden chocar entre sí.
estudiante.numero_documento es NOT NULL, y TIPO_DOCUMENTO admite SIN_DOCUMENTO — un caso real y esperado en niños pequeños. El índice único ux_estudiante_documento es sobre (institucion, tipo_documento, numero_documento). Si dos estudiantes distintos del mismo colegio no tienen cédula, el valor que la app ponga en numero_documento para ambos puede colisionar — el segundo estudiante sin cédula recibiría un 409 como si fuera un duplicado, cuando es un niño distinto.

Ya está corregido (decisión E2, aplicada el 8 de agosto). ux_estudiante_documento es ahora un índice único parcial, el mismo patrón que ya usaban ux_matricula_cursando y ux_curso_titular_vigente. En el SQL se ve así: 
CREATE UNIQUE INDEX "ux_estudiante_documento" ON "estudiante"
  USING btree ("institucion_id","tipo_documento","numero_documento")
  WHERE tipo_documento <> 'SIN_DOCUMENTO';
La unicidad sigue garantizada para quienes tienen cédula o pasaporte; los SIN_DOCUMENTO quedan fuera del índice y ya no colisionan entre sí. Tu endpoint sigue debiendo dar un mensaje claro en el caso legítimo de duplicado (mismo documento real ya registrado) en vez de dejar escapar el error de base de datos.

Parte 5 — Trampas y consejos

No dupliques la identidad. BetterAuth ya tiene user. Tu perfil_usuario la extiende. Es el error más caro de deshacer.

La invitación de BetterAuth no es tu invitación. BetterAuth tiene una invitación para sumar adultos a una organización. La tuya (invitacion_curso) es del dominio y desemboca en registrar un menor con consentimiento. No las mezcles.

Nada se borra. Revocar un vínculo corta el acceso hacia adelante; no borra el histórico. Al finalizar una matrícula, el representante pierde acceso pero la institución conserva los datos.

Todo en UTC — con un matiz. Los timestamptz se guardan en UTC; la conversión a America/Guayaquil ocurre en la pantalla, nunca en la base de datos. Pero las columnas date que representan "qué día ocurrió esto" (como fecha_ingreso) las calcula el servidor explícitamente con la zona horaria correcta — nunca con defaultNow(). Ver §4.1.

Prueba con dos cuentas desde el primer día. Crea dos representantes y dos estudiantes en tus datos de prueba — uno de ellos sin documento. Es la única forma de notar una fuga de permisos o una colisión de constraint antes de que sea tarde.

La cédula ecuatoriana se valida localmente. El algoritmo del dígito verificador (módulo 10) son unas veinte líneas. No busques una API del Registro Civil: no está abierta al público y consultar identidades reales complica el cumplimiento de protección de datos.

No construyas nada para DOCENTE_COLABORADOR. Está diferido a v2 desde el 8 de agosto.
